# 博客 HTTPS 重定向问题解决记录

今天遇到了一个挺折腾的小问题：  
我心血来潮地打开自己的博客,结果浏览器直接弹出：
> SSL_ERROR_BAD_CERT_DOMAIN

我当时一脸懵,以为是 GitHub Pages 崩了,结果仔细一查,问题出在 Cloudflare 的 SSL 模式上。

---

## 🧩 问题现象

我的博客是托管在 GitHub Pages,域名通过 Cloudflare 解析,以便利用其 DNS 加速服务。  
一开始我使用的是 Cloudflare 中的 **自动模式(Auto)**,访问一切正常。  
那时我对 SSL 还不太了解,也没多想。

就在今天我打开网站突然报错 “SSL_ERROR_BAD_CERT_DOMAIN”,  
我就上网查资料,看到很多人说要使用 **Full (strict)** 模式。  
结果我一改过去,页面直接陷入「无限重定向」地狱 😵‍💫。

后来我又动用神秘的Ai力量改成了 “Full” 模式,  
改完之后页面终于恢复正常访问,算是彻底解决。

---

## ⚡️ 出现原理

GitHub Pages 本身会自动为你的仓库签发 HTTPS 证书。  
但这个证书的签发域名一般是`*.github.io`,  
当你绑定自定义域名时,Cloudflare 又会接管一层 HTTPS,就形成了这样一条链：

```
浏览器 ⇄ Cloudflare ⇄ GitHub Pages
```

Cloudflare 的 SSL 模式如下：
```
| 模式 | 含义 | 适用场景 |
|------|------|----------|
| Off | 不加密 | 不推荐 |
| Flexible | 仅浏览器到 Cloudflare 加密 | 源站无 HTTPS |
| Full | 双向加密,但不验证源站证书合法性 | 源站有 HTTPS,但证书不完全匹配 |
| Full (strict) | 双向加密并验证证书合法性 | 源站证书完全匹配域名 |
```
问题就在于：  
**GitHub Pages 的证书虽然有效,但严格模式下 Cloudflare 会要求域名与证书一字不差匹配**,  
而自定义域名往往不在证书签发范围内,于是验证失败。  

更糟的是,Cloudflare 和 GitHub Pages 都在各自做 HTTPS 重定向,  
结果就是——无限循环 ⚙️。

---

## 🧭 解决方案

最终方案其实很简单：

1. 把模式从 **Full (strict)** 改成 **Full**
2. 清除浏览器缓存,等待几分钟
3. 网站恢复正常 🎉

附带检查：
- 确认 GitHub Pages 的 “Enforce HTTPS” 已开启  

---

## 🧠 延伸理解

#### 为什么 “Full” 模式有效？

在 “Full” 模式下,Cloudflare 与源站依然是加密通信的,  
只是它不再强制验证源站证书的合法性。  

这意味着：
- 数据仍然是加密传输的（安全）；  
- 即使源站证书是自签的,也不会导致握手失败。  

对 GitHub Pages 这种不允许手动上传证书的平台来说,  
这反而是最兼容的配置。

---

#### 什么是 SSL/TLS?

我也是第一次接触到这个~

SSL(Secure Sockets Layer)和它的继任版本 TLS(Transport Layer Security)  
是一种 **加密通信协议**,可以保证浏览器与服务器之间的数据传输不被窃听或篡改。  

可以简单理解为：

> 浏览器 ↔ 服务器  
> 两者之间的加密通道

#### 数字证书的作用

SSL 证书就相当于网站的“身份证”。  
由 **CA(Certificate Authority)** 机构签发,里面包含：
- 域名信息  
- 公钥  
- 签发方(CA)
- 有效期等  

浏览器会检查：
1. 证书是否可信；  
2. 证书上的域名与访问域名是否一致；  
3. 是否被篡改或过期。

如果证书签给的是 `github.io`,但你访问的是 `lvdameng.xyz`,  
那就会报错 —— SSL_ERROR_BAD_CERT_DOMAIN。
